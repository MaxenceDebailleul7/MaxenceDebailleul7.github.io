Année 1
AC13.01

Utiliser un système informatique et ses outils.

Ce que j'ai fait

J'ai appris à utiliser les outils informatiques essentiels de la formation : le terminal Linux (une fenêtre où on tape des commandes), l'éditeur de code VS Code, et les outils Python pour écrire et tester des programmes.

Pourquoi je l'ai fait

Avant de pouvoir créer des programmes ou automatiser des tâches, il faut maîtriser les outils qu'on va utiliser. Un mauvais environnement de travail fait perdre beaucoup de temps.

Comment je l'ai fait

Via les modules R1.07, R1.08 et R2.08, en utilisant ces outils quotidiennement pour les TPs et les SAE.

Mes difficultés

S'adapter à de nouveaux outils régulièrement a demandé une veille constante et beaucoup d'auto-formation.

Ce que j'en ai appris

J'ai compris qu'un bon environnement de travail bien configuré dès le départ fait gagner beaucoup de temps sur la durée.

Ce que je ferais autrement

Je prendrais le temps en début de semestre de tout configurer proprement plutôt que de le faire au fil de l'eau.

AC13.02

Lire, exécuter, corriger et modifier un programme.

Ce que j'ai fait

J'ai appris à lire, comprendre et modifier des programmes existants en Python et en Bash : trouver ce qui ne fonctionne pas (les bugs), corriger les erreurs et ajouter de nouvelles fonctionnalités.

Pourquoi je l'ai fait

En entreprise, on travaille rarement sur un code tout neuf. Le plus souvent, on reprend et améliore des scripts déjà existants.

Comment je l'ai fait

Via les modules R1.07 et R2.08, en utilisant le débogueur de VS Code et en lisant la documentation officielle Python.

Mes difficultés

Comprendre la logique d'un code écrit par quelqu'un d'autre, surtout sans commentaires, demande du temps et une lecture très attentive.

Ce que j'en ai appris

J'ai compris l'importance de bien commenter son code pour que les autres puissent le comprendre rapidement.

Ce que je ferais autrement

Avant de modifier du code inconnu, je commenterais d'abord chaque ligne pour m'assurer de bien comprendre ce qu'il fait.

AC13.03

Traduire un algorithme, dans un langage et pour un environnement donné.

Ce que j'ai fait

J'ai écrit des programmes Python à partir d'un algorithme : traduire une suite d'étapes logiques en code exécutable, par exemple des scripts pour calculer des adresses réseau ou traiter des données automatiquement.

Pourquoi je l'ai fait

Automatiser des tâches répétitives avec un script fait gagner énormément de temps. Un administrateur réseau qui sait programmer peut automatiser des dizaines de tâches manuelles.

Comment je l'ai fait

Via les modules R1.07, R2.08 et les SAE, en décomposant chaque problème en petites étapes avant d'écrire le code.

Mes difficultés

Gérer les cas particuliers (une saisie incorrecte, un fichier manquant) sans que le programme plante a été le point le plus difficile à maîtriser.

Ce que j'en ai appris

J'ai compris que la qualité d'un programme ne se mesure pas seulement au fait qu'il fonctionne dans le cas normal, mais aussi à sa robustesse face aux imprévus.

Ce que je ferais autrement

J'écrirais d'abord quelques exemples de ce que le programme doit faire avant de coder, pour mieux définir ce qu'on attend de lui.

AC13.04

Connaître l'architecture et les technologies d'un site Web.

Ce que j'ai fait

J'ai conçu et développé ce portfolio sous forme de site web : création des pages en HTML et CSS, personnalisation du design, et intégration des sections par compétences avec la visionneuse de documents.

Pourquoi je l'ai fait

Ce portfolio est à la fois un livrable de la SAE 1.04 et un outil pour me présenter professionnellement. Créer soi-même son site est aussi une façon de montrer ses compétences techniques.

Comment je l'ai fait

Via les modules R1.09 et R2.09, en partant d'un template et en le personnalisant avec du HTML, CSS et JavaScript.

Ce que je ferais autrement

Je définirais le design sur papier avant de commencer à coder pour éviter de tout refaire plusieurs fois.

AC13.05

Choisir les mécanismes de gestion de données adaptés au développement de l'outil et argumenter ses choix.

Ce que j'ai fait

J'ai comparé différentes façons de stocker des données dans un programme : dans des fichiers simples (texte, CSV, JSON) ou dans une base de données, et j'ai choisi la solution la plus adaptée selon le besoin.

Pourquoi je l'ai fait

Choisir comment stocker les données est une décision importante : le mauvais choix peut rendre un programme lent ou difficile à maintenir.

Comment je l'ai fait

Via les modules R2.07 et R2.08, en manipulant des fichiers CSV et JSON en Python et en écrivant des requêtes SQL sur une base de données SQLite.

Mes difficultés

Comparer objectivement des technologies que je ne maîtrisais pas toutes au même niveau a été difficile.

Ce que j'en ai appris

J'ai appris à choisir une technologie selon les besoins réels du projet plutôt que par habitude.

Ce que je ferais autrement

Je ferais un tableau comparatif dès le début pour formaliser le choix avant de commencer à coder.

AC13.06

S'intégrer dans un environnement propice au développement et au travail collaboratif.

Ce que j'ai fait

J'ai appris à travailler en équipe sur du code avec Git et GitHub : enregistrer chaque modification, revenir en arrière en cas de problème, travailler en parallèle sans écraser le travail des autres, et publier ce portfolio en ligne automatiquement.

Pourquoi je l'ai fait

Git est l'outil de collaboration standard dans tous les métiers du numérique. Ne pas le maîtriser serait un handicap majeur en stage ou en alternance.

Comment je l'ai fait

Via la SAE 1.04 et les projets en groupe, en utilisant Git en ligne de commande et via VS Code, et GitHub pour partager le code et déployer le site.

Mes difficultés

Quand deux personnes modifient le même fichier en même temps, Git ne sait pas quelle version garder. Résoudre ces conflits sans perdre le travail de l'autre demande de la méthode.

Ce que j'en ai appris

J'ai compris que Git n'est pas qu'un outil de sauvegarde : c'est un outil de coordination qui permet à une équipe de travailler efficacement sur le même projet.

Ce que je ferais autrement

Je définirais avec l'équipe dès le départ des règles claires sur qui travaille sur quoi pour éviter les conflits inutiles.
