Année 1
AC13.01

Utiliser un système informatique et ses outils.

Ce que j'ai fait

J'ai pris en main les principaux outils informatiques de la formation : terminal Linux (commandes de base, find, grep, permissions), IDE VS Code (débogueur, extensions, terminal intégré), et outils de développement Python (interpréteur, pip, scripts en ligne de commande).

odification et permissions (-newer, -perm, -size), combinaison avec -exec pour copier ou supprimer automatiquement des fichiers, et distinction entre ls et find pour la recherche récursiveent : terminal, gestionnaire de paquets, débogueur.

Pourquoi je l'ai fait

Maîtriser son environnement de travail est le prérequis de toute activité de développement ou d'administration. Sans outils bien configurés, la productivité est fortement réduite.

Comment je l'ai fait

Via les TPs R1.07 (Fondamentaux de la programmation), R1.08 (Base des systèmes d'exploitation) et R2.08 (Analyse et traitement de données structurées) : utilisation quotidienne du terminal Linux, prise en main de VS Code et de ses extensions Python/Git.

Mes difficultés

M'adapter rapidement à de nouveaux outils au fil des cours (différents IDEs, outils en ligne de commande, gestionnaires de paquets) a demandé une veille constante et beaucoup d'auto-formation.

Ce que j'en ai appris

J'ai développé une capacité d'adaptation rapide à de nouveaux environnements et compris l'importance de bien configurer son outil de travail avant de démarrer un projet.

Ce que je ferais autrement

Je consacrerais du temps en début de semestre à configurer un environnement de développement cohérent et documenté, plutôt que de le construire au fil des besoins.

AC13.02

Lire, exécuter, corriger et modifier un programme.

Ce que j'ai fait

J'ai lu, exécuté et modifié des programmes Python et scripts Bash existants : identification et correction de bugs (erreurs de syntaxe, de logique, gestion des exceptions), et ajout de fonctionnalités à du code fourni.

Pourquoi je l'ai fait

En environnement professionnel, on travaille rarement sur du code vierge. Savoir lire et modifier du code existant est une compétence fondamentale pour maintenir des outils d'administration réseau.

Comment je l'ai fait

Via les TPs R1.07 (Fondamentaux de la programmation) et R2.08 : utilisation du débogueur VS Code, ajout d'affichages de débogage (print/echo), lecture de la documentation officielle Python.

Mes difficultés

Comprendre la logique d'un code écrit par quelqu'un d'autre, surtout sans commentaires, demande du temps et une lecture méthodique ligne par ligne.

Ce que j'en ai appris

J'ai compris l'importance d'un code bien commenté et structuré, et développé une méthode de débogage progressive : reproduire le bug, l'isoler, le corriger, le tester.

Ce que je ferais autrement

Avant de modifier du code inconnu, je prendrais le temps de le commenter entièrement pour m'assurer de bien comprendre sa logique avant toute modification.

AC13.03

Traduire un algorithme, dans un langage et pour un environnement donné.

Ce que j'ai fait

J'ai traduit des algorithmes en programmes Python fonctionnels : écriture de scripts de traitement de données, de calculateurs réseau (sous-réseaux, adressage) et d'outils d'automatisation de tâches simples.

Pourquoi je l'ai fait

L'automatisation par script est un gain de temps majeur en administration réseau. Savoir traduire un besoin métier en code exécutable est une compétence directement valorisable en entreprise.

Comment je l'ai fait

Via les TPs R1.07, R2.08 (Analyse et traitement de données structurées) et les SAÉ : décomposition du problème en étapes (entrées/traitements/sorties), pseudo-code puis implémentation Python avec gestion des erreurs.

Mes difficultés

La gestion des cas limites (entrées invalides, fichiers manquants) et la structuration du code en fonctions réutilisables ont été les points les plus difficiles à maîtriser.

Ce que j'en ai appris

J'ai compris que la qualité d'un algorithme réside dans sa clarté et sa robustesse, pas seulement dans le fait qu'il fonctionne sur le cas nominal.

Ce que je ferais autrement

Je commencerais toujours par écrire quelques cas de test avant le code pour mieux définir le comportement attendu avant d'implémenter.

AC13.04

Connaître l'architecture et les technologies d'un site Web.

Ce que j'ai fait

J'ai conçu et développé ce portfolio sous forme de site web statique en HTML, CSS et JavaScript, en partant d'un template Bootstrap et en le personnalisant pour correspondre au référentiel BUT R&T (structure par compétences, visionneuse de traces).

Pourquoi je l'ai fait

Ce portfolio est à la fois un livrable de la SAÉ 1.04 (Se présenter sur Internet) et un outil professionnel évolutif. Comprendre l'architecture d'un site web est aussi une compétence directement liée au module R1.09 et R2.09.

Comment je l'ai fait

Via R1.09 (Introduction aux technologies Web) et R2.09 (Initiation au développement Web) : HTML/CSS de base, personnalisation du CSS Bootstrap (variables, media queries), structuration des pages et intégration de librairies JS (AOS, Isotope, GLightbox).

Mes difficultés

L'intégration des animations AOS et la mise en page responsive sur mobile ont nécessité de nombreux ajustements. La gestion des chemins relatifs entre fichiers HTML et assets a aussi été source d'erreurs.

Ce que j'en ai appris

J'ai acquis une vision complète du cycle de développement web : conception, développement, test et déploiement via GitHub Pages.

Ce que je ferais autrement

Je définirais la charte graphique et les maquettes des pages avant de coder, pour éviter les refactorisations CSS coûteuses en temps.

AC13.05

Choisir les mécanismes de gestion de données adaptés au développement de l'outil et argumenter ses choix.

Ce que j'ai fait

J'ai comparé et choisi les mécanismes de stockage adaptés aux projets du BUT R&T : fichiers texte, JSON, CSV, et base de données SQLite, en évaluant chaque solution selon les critères du projet (volume, accès, maintenance).

Pourquoi je l'ai fait

Le choix du mécanisme de stockage impacte directement les performances, la maintenabilité et les possibilités d'évolution d'un outil. En réseau, on manipule des données de configuration, des logs et des mesures qui nécessitent des approches différentes.

Comment je l'ai fait

Via R2.07 (Sources de données) et R2.08 (Analyse et traitement de données structurées) : manipulation de fichiers CSV et JSON en Python, requêtes SQL sur SQLite, et comparaison des approches selon les cas d'usage des SAÉ.

Mes difficultés

Comparer objectivement des technologies que je maîtrisais inégalement a été difficile. J'ai dû me documenter sur les solutions que je ne connaissais pas avant de pouvoir les évaluer.

Ce que j'en ai appris

J'ai appris à choisir une technologie en fonction des besoins réels du projet plutôt que par habitude, et à justifier ce choix de façon argumentée.

Ce que je ferais autrement

Je réaliserais un tableau comparatif des solutions dès la phase de conception, pour formaliser l'analyse avant de coder.

AC13.06

S'intégrer dans un environnement propice au développement et au travail collaboratif.

Ce que j'ai fait

Je me suis intégré dans un environnement de développement collaboratif : utilisation de Git (commit, push, pull, branches, résolution de conflits) et GitHub pour versionner le code des SAÉ et déployer ce portfolio via GitHub Pages.

cence de projets, utilisation de l'extension Git intégrée, édition multi-fichiers et configuration du workspace pour les projets Python et web du BUT R&Tt résoudre les conflits de fusion.

Pourquoi je l'ai fait

Le travail collaboratif est la norme en entreprise et Git est l'outil universel de gestion de versions. Ne pas le maîtriser serait un frein majeur en stage ou en alternance.

Comment je l'ai fait

Via la SAÉ 1.04 (Se présenter sur Internet) et les projets de SAÉ en groupe : utilisation de Git en ligne de commande et via VS Code, gestion de branches de fonctionnalités, pull requests sur GitHub, et déploiement automatique sur GitHub Pages.

Mes difficultés

La résolution de conflits lors des fusions de branches m'a déstabilisé au début. Comprendre ce que Git essaie de fusionner et pourquoi il y a un conflit demande de bien visualiser l'historique des commits.

Ce que j'en ai appris

J'ai compris que Git n'est pas qu'un outil de sauvegarde mais un vrai outil de coordination d'équipe. Les commits bien rédigés et les branches thématiques rendent le projet bien plus maintenable.

Ce que je ferais autrement

Je proposerais dès le début du projet une convention de travail écrite (nommage de branches, fréquence des commits) pour éviter les conflits inutiles.
